# InvoiceGuard — build spec (source of truth for all agents)

Accounts-payable payment exception and fraud prevention on **Oracle Forms 12c/14c +
Oracle Database (19c / 23ai Free)**. Three-way match of Purchase Order ↔ Goods Receipt
(GRN) ↔ Supplier Invoice, duplicate and fraud detection, approval-authority and
segregation-of-duties enforcement, hold/release workbench, audit trail.

Design principle (thick database, thin Forms): **every rule lives in PL/SQL packages in
the database**. Forms only collects input, calls the package API, and renders results.
This mirrors Oracle E-Business Suite Payables (holds, hold release, approval) and keeps
the Forms front end replaceable later (modernisation to APEX / web) without touching rules.

Schema owner: `IG`. All objects prefixed `IG_`. Functional currency: `INR`.

---

## 1. Tables

Standard columns on transactional tables: `created_by VARCHAR2(30)`, `created_date DATE
DEFAULT SYSDATE`, `last_updated_by VARCHAR2(30)`, `last_updated_date DATE`.
PKs from identity columns (`GENERATED BY DEFAULT AS IDENTITY`) — works on 19c and 23ai.

| Table | Key columns |
|---|---|
| `IG_USERS` | user_id PK, user_name UK (upper), full_name, role CHECK IN ('AP_CLERK','AP_MANAGER','FIN_CONTROLLER','BUYER','RECEIVER','AUDITOR'), approval_limit NUMBER (INR, 0 for non-approvers), active_flag CHECK Y/N |
| `IG_VENDORS` | vendor_id PK, vendor_num UK, vendor_name, gstin VARCHAR2(15), pan VARCHAR2(10), status CHECK IN ('ACTIVE','INACTIVE','BLOCKED'), payment_terms_days, risk_category CHECK IN ('LOW','MEDIUM','HIGH') default LOW |
| `IG_VENDOR_BANK_ACCTS` | bank_acct_id PK, vendor_id FK, account_num VARCHAR2(30), ifsc VARCHAR2(11), effective_from DATE, active_flag, created_by, created_date. Only one active per vendor (enforced in package/trigger) |
| `IG_PO_HEADERS` | po_header_id PK, po_num UK, vendor_id FK, po_date, currency, status CHECK IN ('OPEN','CLOSED','CANCELLED'), buyer_user FK→IG_USERS.user_name |
| `IG_PO_LINES` | po_line_id PK, po_header_id FK, line_num, item_code, description, uom, qty_ordered > 0, unit_price >= 0, tax_rate (percent, e.g. 18). UK(po_header_id,line_num) |
| `IG_RECEIPTS` | receipt_id PK, receipt_num UK, po_header_id FK, receipt_date, received_by (user_name) |
| `IG_RECEIPT_LINES` | receipt_line_id PK, receipt_id FK, po_line_id FK, qty_received >= 0, qty_rejected >= 0 default 0 |
| `IG_INVOICES` | invoice_id PK, vendor_id FK, invoice_num, invoice_num_norm (set by trigger via `ig_util_pkg.normalize_invoice_num`), invoice_date, received_date default SYSDATE, po_header_id FK, currency default 'INR', exchange_rate default 1, invoice_amount (gross, incl tax), tax_amount, base_amount (= invoice_amount*exchange_rate, set by trigger), bank_acct_id FK (remit-to), status CHECK IN ('DRAFT','ON_HOLD','VALIDATED','APPROVED','REJECTED','PAID','CANCELLED') default DRAFT, risk_score NUMBER default 0, entered_by, approved_by, approved_date, payment_ref, paid_date, description |
| `IG_INVOICE_LINES` | invoice_line_id PK, invoice_id FK ON DELETE CASCADE, line_num, po_line_id FK, qty_billed > 0, unit_price >= 0, line_amount (= qty*price, set by trigger). UK(invoice_id,line_num) |
| `IG_HOLD_CODES` | hold_code PK VARCHAR2(20), description, severity CHECK IN ('HIGH','MEDIUM','LOW'), risk_weight NUMBER, release_role (NULL = cannot be released; invoice must be cancelled), category CHECK IN ('MATCH','DUPLICATE','FRAUD','COMPLIANCE','AUTHORITY') |
| `IG_SETTINGS` | param_name PK, num_value, description |
| `IG_INVOICE_HOLDS` | hold_id PK, invoice_id FK, invoice_line_id FK NULL, hold_code FK, hold_reason VARCHAR2(400), hold_date, status CHECK IN ('OPEN','RELEASED') default OPEN, released_by, release_date, release_reason |
| `IG_APPROVAL_HISTORY` | approval_id PK, invoice_id FK, user_name, action CHECK IN ('APPROVE','REJECT','RELEASE_HOLD','CANCEL','PAY','SCAN'), outcome CHECK IN ('SUCCESS','BLOCKED'), reason VARCHAR2(400), action_date |
| `IG_AUDIT_LOG` | audit_id PK, entity_name, entity_id, action, old_value VARCHAR2(4000), new_value VARCHAR2(4000), user_name, action_ts TIMESTAMP default SYSTIMESTAMP |

Indexes on all FKs, plus `IG_INVOICES(vendor_id, invoice_num_norm)`, `IG_INVOICES(vendor_id, invoice_date)`,
`IG_INVOICE_HOLDS(status, hold_code)`.

### Seeded `IG_SETTINGS`

| param_name | num_value | meaning |
|---|---|---|
| PRICE_TOL_PCT | 2 | invoice unit price may exceed PO price by this % |
| PRICE_TOL_ABS | 1 | …and by more than this absolute amount before a hold |
| QTY_TOL_PCT | 0 | billed qty may exceed net received qty by this % |
| AMOUNT_TOL_ABS | 1 | header amount vs lines+tax rounding tolerance |
| TAX_TOL_ABS | 1 | tax amount vs expected (sum line_amount*tax_rate/100) |
| DUP_WINDOW_DAYS | 30 | suspected duplicate window (same vendor, same amount) |
| BANK_CHANGE_DAYS | 30 | remit-to bank account changed within N days → hold |
| SPLIT_WINDOW_DAYS | 7 | split-invoice detection window |
| SPLIT_THRESHOLD | 500000 | approval tier boundary used by split detection (INR) |
| SPLIT_BAND_PCT | 85 | invoice is "just under" if ≥ this % of threshold |
| ROUND_AMOUNT_MIN | 100000 | round-amount check only applies at or above this base amount |
| FUTURE_DATE_DAYS | 0 | invoice_date may be at most N days after SYSDATE |

### Seeded `IG_HOLD_CODES`

| hold_code | category | severity | weight | release_role | rule (all evaluated by `ig_match_pkg.validate_invoice`) |
|---|---|---|---|---|---|
| DUP_EXACT | DUPLICATE | HIGH | 60 | NULL | another non-cancelled invoice, same vendor, same `invoice_num_norm` |
| DUP_SUSPECT | DUPLICATE | HIGH | 40 | AP_MANAGER | same vendor + same base_amount + invoice_date within DUP_WINDOW_DAYS (different number) **or** same invoice_num_norm + same amount at a *different* vendor |
| PRICE_VAR | MATCH | MEDIUM | 20 | AP_MANAGER | line unit_price > po unit_price*(1+PRICE_TOL_PCT/100) and difference per unit > PRICE_TOL_ABS (line-level hold) |
| QTY_REC | MATCH | MEDIUM | 20 | AP_MANAGER | cumulative billed qty on the PO line (all non-cancelled/non-rejected invoices, incl. this) > net received (received − rejected)*(1+QTY_TOL_PCT/100) (line-level) |
| QTY_ORD | MATCH | HIGH | 30 | FIN_CONTROLLER | cumulative billed qty > qty_ordered (line-level) |
| NO_RECEIPT | MATCH | MEDIUM | 25 | AP_MANAGER | PO line has no receipt lines at all (line-level) |
| AMT_MISMATCH | MATCH | MEDIUM | 15 | AP_MANAGER | abs(invoice_amount − (sum line_amount + tax_amount)) > AMOUNT_TOL_ABS |
| TAX_VAR | COMPLIANCE | LOW | 10 | AP_MANAGER | abs(tax_amount − sum(line_amount*po tax_rate/100)) > TAX_TOL_ABS |
| PO_VENDOR | FRAUD | HIGH | 50 | FIN_CONTROLLER | invoice vendor ≠ PO vendor, or invoice line's PO line belongs to a different PO than the header |
| PO_STATUS | MATCH | MEDIUM | 20 | AP_MANAGER | PO not OPEN |
| VENDOR_STATUS | FRAUD | HIGH | 50 | FIN_CONTROLLER | vendor INACTIVE or BLOCKED |
| BANK_CHANGE | FRAUD | HIGH | 45 | FIN_CONTROLLER | remit-to bank account effective_from within BANK_CHANGE_DAYS of SYSDATE, or remit-to account not the vendor's active account, or the same account_num is registered to another vendor |
| DATE_ANOMALY | FRAUD | MEDIUM | 15 | AP_MANAGER | invoice_date < po_date, or invoice_date > SYSDATE + FUTURE_DATE_DAYS |
| SPLIT_SUSPECT | FRAUD | HIGH | 35 | FIN_CONTROLLER | ≥2 non-cancelled invoices (incl. this) of the same vendor within SPLIT_WINDOW_DAYS, each base_amount ≥ SPLIT_THRESHOLD*SPLIT_BAND_PCT/100 and < SPLIT_THRESHOLD, and their sum ≥ SPLIT_THRESHOLD |
| GSTIN_INVALID | COMPLIANCE | MEDIUM | 15 | AP_MANAGER | vendor GSTIN fails `ig_util_pkg.valid_gstin` (format + check digit) or GSTIN chars 3–12 ≠ PAN |
| ROUND_AMT | FRAUD | LOW | 5 | AP_MANAGER | base_amount ≥ ROUND_AMOUNT_MIN and MOD(base_amount, 10000)=0 |
| UNAUTH_APPROVAL | AUTHORITY | HIGH | 60 | FIN_CONTROLLER | placed by `ig_audit_pkg.scan_approvals` on an already APPROVED/PAID invoice whose approver lacked authority (see §3.4) |

Risk score = LEAST(100, sum(risk_weight) of OPEN holds + 10 if vendor risk_category='HIGH'
+ 5 if 'MEDIUM'). Recomputed on validate, release and scan.

## 2. Triggers (DB)
- `ig_invoices_biu`: set invoice_num_norm, base_amount, last_updated_*; block updates of
  amounts/vendor/PO/lines when status in ('APPROVED','PAID','CANCELLED') → ORA-20010.
- `ig_invoice_lines_biu`: line_amount := ROUND(qty_billed*unit_price,2); block DML when parent
  invoice status not in ('DRAFT','ON_HOLD','VALIDATED') → ORA-20010. Any line or header
  amount change on a VALIDATED invoice resets status to DRAFT (handled in package call or
  compound trigger — must re-validate before approval).
- `ig_invoices_aud`: audit status changes and amount changes into IG_AUDIT_LOG.
- `ig_bank_accts_aud`: audit every bank account insert/update (fraud trail).
- `ig_vendors_aud`: audit status / GSTIN changes.

## 3. PL/SQL packages (public API — Forms calls exactly these)

All errors are raised with `RAISE_APPLICATION_ERROR` using these codes (constants in
`ig_util_pkg`):

| code | meaning |
|---|---|
| -20001 | unknown / inactive application user |
| -20002 | invoice not found |
| -20003 | invalid status for this action |
| -20004 | open holds exist |
| -20005 | approval limit exceeded |
| -20006 | segregation of duties violation |
| -20007 | role not authorised for this action / hold |
| -20008 | hold cannot be released (invoice must be cancelled) |
| -20009 | reason is mandatory |
| -20010 | record locked (invoice approved/paid/cancelled) |
| -20011 | invoice has no lines |

Message text format: `IG-nnnnn: <human readable sentence>` so Forms can show it directly.

### 3.1 `ig_util_pkg`
- `FUNCTION normalize_invoice_num(p VARCHAR2) RETURN VARCHAR2` — UPPER, remove all
  non-alphanumerics, strip leading zeros of each numeric run (so `INV-01001`, `inv 1001`,
  `INV1001` all → `INV1001`). DETERMINISTIC.
- `FUNCTION valid_gstin(p VARCHAR2) RETURN VARCHAR2` ('Y'/'N') — 15 chars, pattern
  `^[0-9]{2}[A-Z]{5}[0-9]{4}[A-Z][1-9A-Z]Z[0-9A-Z]$`, state code 01–38 (and 97/99), and the
  GSTN mod-36 check digit (base-36 chars 0-9A-Z, factors alternate 1,2 from the left over
  the first 14 chars, product → quotient+remainder by 36, sum, check = (36 − sum mod 36) mod 36).
- `FUNCTION get_setting(p_name VARCHAR2) RETURN NUMBER`.
- `PROCEDURE log_audit(p_entity, p_entity_id, p_action, p_old, p_new)` — autonomous.
- `PROCEDURE log_approval(p_invoice_id, p_action, p_outcome, p_reason)` — AUTONOMOUS
  TRANSACTION so BLOCKED attempts are recorded even when the caller rolls back.

### 3.2 `ig_session_pkg`
- `PROCEDURE set_user(p_user_name VARCHAR2)` — validates active user in IG_USERS (else -20001), stores in package state.
- `FUNCTION current_user RETURN VARCHAR2`, `FUNCTION current_role RETURN VARCHAR2`.
  All other packages use `current_user` for created_by/approved_by/released_by and audit.
  If not set, falls back to `SYS_CONTEXT('USERENV','SESSION_USER')` mapped to IG_USERS if present, else raises -20001 for write actions.

### 3.3 `ig_match_pkg`
- `FUNCTION validate_invoice(p_invoice_id NUMBER) RETURN NUMBER` — returns count of OPEN holds after validation.
  Steps: lock invoice; require status IN ('DRAFT','ON_HOLD','VALIDATED') (else -20003); require ≥1 line (-20011);
  delete OPEN system holds of this invoice (keep RELEASED ones — a released hold for the
  same code + same line is **not** re-placed unless the underlying numbers changed, i.e.
  keep released holds sticky: do not re-place a hold code/line that has a RELEASED row
  newer than the invoice's last_updated_date); run every rule in §1; insert holds;
  recompute risk_score; status := ON_HOLD if open holds > 0 else VALIDATED; audit.
- `FUNCTION open_hold_count(p_invoice_id) RETURN NUMBER`.
- `PROCEDURE validate_all_draft` — batch validation of all DRAFT/ON_HOLD invoices (for a scheduler job).
- `PROCEDURE recompute_risk(p_invoice_id)`.

### 3.4 `ig_workflow_pkg`
- `PROCEDURE approve_invoice(p_invoice_id NUMBER, p_comment VARCHAR2 DEFAULT NULL)`
  Order of checks, each failure logs a BLOCKED row in IG_APPROVAL_HISTORY (autonomous) then raises:
  1. status = 'VALIDATED' (-20003) and open holds = 0 (-20004);
  2. current role IN ('AP_MANAGER','FIN_CONTROLLER') (-20007);
  3. base_amount ≤ user's approval_limit (-20005);
  4. SoD (-20006): approver ≠ invoice entered_by, ≠ PO buyer_user, ≠ any receiver of the PO's receipts;
  then status APPROVED, approved_by/date, SUCCESS row.
- `PROCEDURE reject_invoice(p_invoice_id, p_reason)` — reason mandatory (-20009); role AP_MANAGER/FIN_CONTROLLER; status from DRAFT/ON_HOLD/VALIDATED → REJECTED.
- `PROCEDURE cancel_invoice(p_invoice_id, p_reason)` — reason mandatory; any role except AUDITOR/BUYER/RECEIVER; not PAID; status → CANCELLED; open holds → RELEASED with reason 'Invoice cancelled'.
- `PROCEDURE release_hold(p_hold_id NUMBER, p_reason VARCHAR2)` — reason mandatory (-20009);
  hold must be OPEN; release_role NULL → -20008; user role must equal release_role or be
  FIN_CONTROLLER (-20007); release_role AP_MANAGER also releasable by FIN_CONTROLLER; SoD: releaser ≠ entered_by (-20006).
  Mark RELEASED; recompute risk; if no open holds remain and invoice ON_HOLD → VALIDATED. Log approval history RELEASE_HOLD.
- `PROCEDURE mark_paid(p_invoice_id, p_payment_ref)` — status must be APPROVED, open holds = 0 (UNAUTH_APPROVAL blocks payment), role FIN_CONTROLLER; → PAID.

### 3.5 `ig_audit_pkg`
- `FUNCTION scan_approvals RETURN NUMBER` — post-facto detective control: for APPROVED/PAID
  invoices, find approved_by not an active approver, or base_amount > that user's
  approval_limit, or SoD violation (approved_by = entered_by / PO buyer / receiver). Place an
  OPEN `UNAUTH_APPROVAL` hold (once per invoice) with the reason, recompute risk. Return count of new holds.
- `FUNCTION vendor_risk_summary` not needed — use views.

## 4. Views
- `IG_EXCEPTION_QUEUE_V` — one row per OPEN hold: hold_id, invoice_id, invoice_num, vendor_num, vendor_name, po_num, base_amount, hold_code, category, severity, hold_reason, line_num, hold_date, age_days, risk_score, release_role, entered_by.
- `IG_MATCH_DETAIL_V` — one row per invoice line: invoice_id, line_num, po_num, po_line_num, item_code, qty_ordered, qty_received_net, qty_billed_this, qty_billed_cum, po_unit_price, inv_unit_price, price_var_pct, line_amount, match_status ('MATCHED' / 'EXCEPTION' if any open line-level hold).
- `IG_DASHBOARD_V` — per hold_code: open_count, open_amount (sum base_amount of distinct invoices), released_count.
- `IG_KPI_V` — single row: invoices_total, on_hold, validated, approved, paid, amount_on_hold, amount_prevented (base_amount of invoices CANCELLED/REJECTED that had a DUPLICATE or FRAUD hold), blocked_approval_attempts, first_pass_match_rate (% invoices validated with zero holds ever).
- `IG_VENDOR_RISK_V` — per vendor: invoice count, hold count, high-severity holds, bank changes in 90 days, risk_category.
- LOV views: `IG_VENDORS_LOV_V` (ACTIVE+others with status shown), `IG_PO_LOV_V` (po_num, vendor, status), `IG_PO_LINES_LOV_V` (po_header_id, po_line_id, line_num, item_code, description, unit_price, qty_ordered), `IG_USERS_LOV_V`.

## 5. Seed data (relative to SYSDATE so rules stay valid any day)
Users: `CLERK1` (AP_CLERK, 0), `CLERK2` (AP_CLERK, 0), `APMGR1` (AP_MANAGER, 500000), `APMGR2` (AP_MANAGER, 500000),
`FINCTRL1` (FIN_CONTROLLER, 10000000), `BUYER1` (BUYER, 0), `RECV1` (RECEIVER, 0), `AUDIT1` (AUDITOR, 0).
Vendors (≥6, Indian-style names, valid GSTINs computed with the real check digit; one deliberately invalid; one INACTIVE; one HIGH risk).
POs, receipts, invoices covering **every hold code at least once**, plus ≥4 fully clean
invoices that validate with zero holds, one invoice approved legacy-style by BUYER1 above
limit (for UNAUTH_APPROVAL scan), and one shared bank account across two vendors.
A scenario table in `db/README_SCENARIOS.md`: invoice_num → expected hold codes.

## 6. Tests (`db/tests/run_tests.sql`)
SQL*Plus script, `SET SERVEROUTPUT ON`, prints `PASS`/`FAIL <name>` per check and a final
`SUMMARY: n passed, m failed`. Covers: normalize_invoice_num cases, valid_gstin good/bad,
each hold code fires on its scenario and does not fire on clean invoices, approve success,
approve blocked for each of -20003/-20004/-20005/-20006/-20007 and BLOCKED row persisted,
release_hold role checks and -20008 on DUP_EXACT, released holds stay released on re-validate,
cancel releases holds, mark_paid blocked by UNAUTH_APPROVAL, scan_approvals finds the legacy
invoice, line lock after approval (-20010). Tests run inside a savepoint / end in ROLLBACK
except where autonomous logging is the thing being tested.

## 7. Oracle Forms modules (`forms/`)
Target Forms 12.2.1.x / 14.1.2. Sources kept as **Forms XML** (`*_fmb.xml`, convertible with
`frmxml2f`) + PL/SQL library text `IG_LIB.pld` + menu XML, plus `FORM_DESIGN.md` build sheet as fallback.

| Module | Purpose |
|---|---|
| `IG_MAIN` | Login (user name LOV from IG_USERS → `ig_session_pkg.set_user`, store in `:GLOBAL.IG_USER`), KPI dashboard (IG_KPI_V, IG_DASHBOARD_V), launcher buttons |
| `IG_INVOICE` | Invoice workbench. Blocks: INV_HDR (IG_INVOICES, form layout), INV_LINES (IG_INVOICE_LINES, tabular, detail of INV_HDR), MATCH (IG_MATCH_DETAIL_V, read-only), HOLDS (IG_INVOICE_HOLDS + hold code desc, read-only, detail), CTRL (non-db buttons). Buttons: Validate, Approve, Reject, Cancel, Release Hold, Mark Paid, Audit Trail. Parameter `P_INVOICE_ID` for drill-down. LOVs: vendor, PO, PO line, bank acct. Severity visual attributes (VA_HIGH red, VA_MEDIUM amber, VA_LOW plain) on hold rows; risk score colour. Status drives item enable/disable. |
| `IG_EXCEPTIONS` | Exception workbench on IG_EXCEPTION_QUEUE_V: filter by category/severity/hold code/vendor/age, Release (asks reason), Open Invoice (CALL_FORM IG_INVOICE with P_INVOICE_ID), Run Approval Scan button (`ig_audit_pkg.scan_approvals`), Validate All button. |
| `IG_PO_GRN` | PO header/lines and receipts (GRN) entry/inquiry, master-detail-detail. |
| `IG_SETUP` | Tab canvas: Vendors + bank accounts (detail), Users & approval limits, Settings (tolerances), Hold codes (read-only). |
| `IG_MENU` (.mmb) | Navigation menu used by all forms. |
| `IG_LIB` (.pll) | `ig_msg.show_error(p_err VARCHAR2 DEFAULT NULL)` (parses the IG- text from `p_err`, which handlers pass as SQLERRM; with no argument, as in ON-ERROR, it uses the Forms ERROR_* built-ins and shows an alert), `ig_ui.set_severity_va`, `ig_nav.open_invoice(id)`, `ig_ui.ask_reason RETURN VARCHAR2` (reason dialog). |

Every button `WHEN-BUTTON-PRESSED` calls exactly one package API inside
`BEGIN … EXCEPTION WHEN OTHERS THEN ig_msg.show_error(SQLERRM); END;`, then `COMMIT_FORM`/
`EXECUTE_QUERY` to refresh. Forms never updates `status`, `risk_score`, `approved_by`, or holds directly.
